\chapter{Evaluation}
\label{chap:evaluation}

This chapter evaluates the correctness and performance of the Pseudo++
toolchain.  The evaluation is structured into three tiers: unit tests for
the formatter module, integration tests that execute official Romanian
baccalaureate problems end-to-end, and semantic-preservation tests for the
loop equivalence module.  Transpiler correctness is assessed by compiling the
generated C code with GCC and comparing its output against the known-correct
interpreter results.

% ─────────────────────────────────────────────────────────────────────────────
\section{Testing Methodology}
\label{sec:methodology}

The test suite is divided into two directories:

\begin{itemize}
  \item \texttt{test/} --- C unit tests compiled and run by the build system
        (\texttt{make test}).  Each test file exercises a single module in
        isolation.

  \item \texttt{int-test/} --- integration tests organised into two
        sub-trees:
        \begin{itemize}
          \item \texttt{int-test/bac/\textit{year}/antrenament\textit{N}/}
                --- one directory per baccalaureate training problem, each
                containing the canonical source (\texttt{src.pseudo}), the
                formatter-normalised source (\texttt{cleaned-src.pseudo}),
                an input file (\texttt{input.txt}), and the
                expected output (\texttt{expected-output.txt}).
          \item \texttt{int-test/equivalence/\textit{A\_to\_B}/} --- one
                directory per directed loop conversion, each containing the
                source (\texttt{src.pseudo}), the target loop type
                (\texttt{target.txt}), the 0-based line index of the loop
                (\texttt{loop\_line.txt}), optional input (\texttt{input.txt}),
                and the expected execution output (\texttt{expected-output.txt}).
        \end{itemize}
\end{itemize}

All integration tests are run by invoking the \texttt{pseudo} CLI binary
directly with the normalised source and the provided input.  The output is
compared byte-for-byte against the expected file.

% ─────────────────────────────────────────────────────────────────────────────
\section{Unit Testing}
\label{sec:unit-tests}

The formatter module is covered by 39 unit tests in \texttt{test/test\_linter.c}.
Each test constructs a short input string, calls \texttt{linter\_run()}, and
asserts the normalised output against a known-correct string using a simple
\texttt{ASSERT\_STR\_EQ} macro.  The cases cover:

\begin{itemize}
  \item Symbol substitution for all entries in the substitution table
        (assignment arrow, relational operators, block-close square,
        box-drawing bar, smart quotes, Romanian diacritics).
  \item Greedy, maximum-munch ordering: ensuring that a two-byte Unicode
        sequence is matched as a single token rather than as two separate
        ASCII characters.
  \item Edge cases: empty input, a string consisting entirely of replacement
        sequences, and replacements at the start and end of the input.
  \item Keyword normalisation: the diacritic variants of Romanian keywords
        (\texttt{cite\c{s}te} / \texttt{cite\c{s}te}, \texttt{c\^{a}t~timp},
        \texttt{p\^{a}n\u{a}~c\^{a}nd}, etc.) are mapped to their
        ASCII equivalents.
  \item Structural re-indentation: pipe-indented and box-drawing-indented
        source is correctly flattened and re-indented.
\end{itemize}

All 39 unit tests pass.

\section{Integration Testing on Baccalaureate Examination Problems}
\label{sec:bac-tests}

\subsection{Dataset Description}
\label{subsec:dataset}

The integration test dataset consists of 53 pseudocode problems drawn from
the official Romanian baccalaureate training sets published by the Ministry
of Education for examination years 2020 through 2025
\cite{romanian-curriculum}.
Table~\ref{tab:bac-dataset} shows the breakdown by year.

\begin{table}[h]
\centering
\small
\begin{tabular}{c r}
\hline
\textbf{Year} & \textbf{Problems} \\
\hline
2020 & 20 \\
2021 & 12 \\
2022 &  5 \\
2023 &  5 \\
2024 &  5 \\
2025 &  6 \\
\hline
\textbf{Total} & \textbf{53} \\
\hline
\end{tabular}
\caption{Baccalaureate integration test dataset by year.}
\label{tab:bac-dataset}
\end{table}

The problems cover the full range of constructs present in the dialect:
all four loop forms, nested conditionals, string and integer arithmetic,
the floor-division and modulo operators, and multi-variable
\texttt{citeşte} statements.  Each problem is supplied with one or more
input values and a single expected output string.

\subsection{Results}
\label{subsec:results}

The interpreter correctly produces the expected output for all
\textbf{53 out of 53} problems (\textbf{100\,\%}).  No failures were
observed across any of the six examination years.

\section{Transpiler Correctness Verification}
\label{sec:transpiler-eval}

Transpiler correctness is verified for the C target using the 32 problems
from the 2020 and 2021 baccalaureate sets (the subset for which reference
input-output pairs were available at transpiler evaluation time).  For each
problem the following pipeline is executed automatically:

\begin{enumerate}
  \item Run \texttt{pseudo transpile c \textit{src}} to produce a C source
        file.
  \item Compile the generated C with \texttt{gcc -lm}.
  \item Execute the compiled binary with the same input as the interpreter
        test and compare its standard output against the reference.
\end{enumerate}

All \textbf{32 out of 32} problems (\textbf{100\,\%}) produce compilable C
code whose output matches the interpreter reference exactly.  GCC reported
no compilation errors or warnings for any of the generated files.

\section{Loop Equivalence Semantic Preservation}
\label{sec:equivalence-eval}

The equivalence module is evaluated with 9 directed conversion tests, one
for each ordered pair among the four loop constructs that changes the loop
type:

\begin{center}
\small
\begin{tabular}{ll}
\hline
\textbf{Source} & \textbf{Target} \\
\hline
\texttt{for}         & \texttt{while}    \\
\texttt{for}         & \texttt{do-while} \\
\texttt{for}         & \texttt{repeat}   \\
\texttt{while}       & \texttt{do-while} \\
\texttt{while}       & \texttt{repeat}   \\
\texttt{do-while}    & \texttt{while}    \\
\texttt{do-while}    & \texttt{repeat}   \\
\texttt{repeat}      & \texttt{while}    \\
\texttt{repeat}      & \texttt{do-while} \\
\hline
\end{tabular}
\end{center}

For each test, the module transforms the source loop, writes the result to a
temporary file, and the interpreter executes that file with the original
input.  The execution output is then compared against the expected result
produced by running the untransformed program.

All \textbf{9 out of 9} transformations (\textbf{100\,\%}) preserve the
program's observable output exactly, confirming that the rewrite rules
described in Section~\ref{sec:loop-equivalence} are implemented correctly.

\section{Performance Analysis}
\label{sec:performance}

Execution time was measured by running each of the 32 baccalaureate problems
(2020--2021) 100 times in sequence and computing the mean wall-clock time per
run on an AMD Ryzen 5 3600 machine running Arch Linux with a release build
(\texttt{-O3}).  The average execution time per problem was \textbf{2.4\,ms},
with a total time of \textbf{76.8\,ms} for all 32 problems combined.
The dominant cost in each run is process start-up and the Tree-sitter parse,
not the interpreter loop itself.

At 2.4\,ms per program the interpreter is fast enough for interactive use:
a student pressing the \textbf{Run} button receives output well within the
threshold of perceived immediacy (\textless{}100\,ms for a single-line
response).  The step-by-step debugger incurs additional overhead per step due
to snapshot serialisation, but this overhead is negligible compared to the
human reaction time between debugger clicks.

\section{Discussion}
\label{sec:discussion}

The evaluation demonstrates that the Pseudo++ toolchain correctly handles all
53 baccalaureate problems tested, covering examination years 2020 through
2025.  The transpiler generates valid, warnings-free C code for every problem
in the verification subset.  Loop equivalence transformations preserve
observable output in all nine directed-conversion cases.

Several limitations should be noted.  First, the test dataset consists
exclusively of single-function programs with simple integer arithmetic; the
dialect does not support user-defined functions or arrays, so these
constructs were not exercised.  Second, transpiler
verification was performed only for the C target; the C++ and Pascal backends
share the same emission logic but were not independently benchmarked.  Third,
the performance figures reflect CLI execution on a desktop machine; browser
performance under the WebAssembly runtime was not formally measured, though
informal testing confirms sub-100\,ms response times for all tested problems.
